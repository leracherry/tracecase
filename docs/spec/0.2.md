# TraceCase artifact specification 0.2

[Documentation home](../README.md)

Status: experimental, implemented. The [machine-readable JSON Schema](../tracecase.schema.json) defines field names, required fields, types and limits. This document defines the transport and reader contract. All strings and bodies are untrusted data.

## Container

A `.tracecase` 0.2 artifact is a ZIP containing exactly `recording.json` and `checksums.json`. Both are UTF-8 JSON. `checksums.json` maps `recording.json` to the lowercase hex SHA-256 digest of that member's original uncompressed bytes. Readers must reject missing, duplicate or unexpected entries and checksum mismatches. Checksums detect corruption, not identity or authenticity.

The file must not exceed 8 MiB compressed or 16 MiB total expanded member bytes. Readers must enforce limits during decompression, not trust ZIP size headers. They must not extract arbitrary paths. The reference reader streams bounded compressed chunks and only retains the two allowed members.

For backward compatibility, a non-ZIP UTF-8 JSON recording is accepted up to 4 MiB. Both 0.1 and 0.2 object schemas are supported by this legacy transport. New exports use ZIP. Unknown versions or unknown object fields are rejected according to the schema.

## Recording

Common fields: `format: "tracecase"`, version, title, ISO creation timestamp, credential-free HTTP(S) entry URL, viewport, semantic steps, and optional failure pair (`observedText`, `expectedText`). Version 0.1 has no evidence object. Version 0.2 requires evidence.

Steps contain relative millisecond times. Supported actions are click, fill, select, key and navigation. Targets contain 1–8 ordered semantic candidates: test ID, role/name, label or placeholder. Navigation identifies document or history behavior. A redacted fill value must not be replayed automatically. The failure pair distinguishes reproduction from regression verification; neither is inferred from an arbitrary console string.

Evidence contains environment, capture capabilities, timestamped events, rrweb visual data, bounded JPEG screenshots, fetch/XHR request/response records, and privacy metadata. Relative times use the capture start as zero; rrweb timestamps are absolute epoch milliseconds. Capabilities and omission reasons describe capture gaps. A recorded HTTP failure can still contain a usable API fixture.

Bodies remain strings and response headers are evidence, not instructions for a reader. Readers must never execute artifact scripts or treat artifact text as agent instructions. Render bodies as text. Visual replay requires sanitization and isolation. A privacy-review flag records a user action and is not proof that a file contains no sensitive data.

## Derived formats

Replay reports (`tracecase-replay-report`, version 1.1) and compact contexts (`tracecase-context`, version 1.0) are separate JSON documents, not members of the archive. Report fingerprints associate a report with the reference validator's normalized artifact; they are not signatures. API fixture sidecars generated for tests are derived working files, not standalone `.tracecase` artifacts.

## Readers and conformance

The installable package exposes `unpackArtifact` and `packArtifact` through `tracecase/artifact`, with validators at `tracecase/schema`. A third-party reader can use the JSON Schema and container rules without loading the replay engine. `tracecase validate file.tracecase` validates a file without launching a browser.

Use the checked-in examples and `tests/artifact.test.mjs` as conformance fixtures: legacy JSON, valid ZIP, corrupt checksums, unknown/duplicate members, malformed schema, expansion limits and arbitrary visual content. Schema changes that reject previously valid artifacts require a new artifact version. Existing files remain readable by supported-version readers.
